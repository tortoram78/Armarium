# Armarium — Vercel + Supabase deploy runbook

This document covers the complete deployment path for Phase 2: Vercel (hosting + serverless
functions) backed by Supabase Postgres. It is deliberately concrete — exact variable names, exact
command sequences, and explicit notes on what each variable controls.

---

## Environment variables

| Variable | Required | Default / behaviour when absent |
|---|---|---|
| `DATABASE_URL` | For persistence | Absent: in-memory repository (ephemeral, no DB needed) |
| `ANTHROPIC_API_KEY` | For live classification + NL parsing | Absent: offline heuristic / corpus |
| `APP_PASSWORD` | For the one-password gate | Absent: gate disabled, app is open |
| `ARMARIUM_USER_ID` | For seeding a specific user | `00000000-0000-0000-0000-000000000001` |

**Where to set them:**
- **Vercel:** Project Settings > Environment Variables. Scope to Production / Preview / Development
  as appropriate. `DATABASE_URL` and `ANTHROPIC_API_KEY` should be Production + Preview.
  `APP_PASSWORD` should be Production.
- **Local dev:** `.env.local` at the repo root (gitignored by `.gitignore`). Never commit secrets.
  Format: one `KEY=value` per line; Next.js loads this file automatically.

### What each variable does

**`DATABASE_URL`** (Postgres connection string, e.g. `postgresql://user:pw@host:5432/db`)

The client is a lazy singleton in `src/db/client.ts` — the connection is opened on the first
query, never at module load. This means:
- `pnpm typecheck`, `pnpm lint`, `pnpm test`, and `pnpm build` all pass with no `DATABASE_URL`
  set. Do not add this to CI unless you are running migration/seed steps.
- When absent at runtime, `getRepository()` in `src/server/services.ts` returns the in-memory
  `memoryRepository`. Data is ephemeral (lost on cold start / restart); useful for demos and
  local dev without a database.
- When set, `getRepository()` returns `postgresRepository` which reads all items from the
  `classification` jsonb column as the lossless source of truth.

Supabase provides the connection string under Project Settings > Database > Connection string
(use the "URI" format). For serverless, use the **pooled** connection string (port 6543) with
`?pgbouncer=true&connection_limit=1` appended to avoid connection exhaustion.

**`ANTHROPIC_API_KEY`**

When set, `getClassifier()` wires the live Anthropic classification pipeline
(`src/core/classify/classify.ts`) using model `MODEL_ID` (currently `claude-sonnet-4-6`,
defined in `src/core/config.ts`). `getTripParser()` wires the live NL trip parser
(`parseTripConditions`).

When absent:
- Classification falls back to `classifyOffline` — the pre-validated seed corpus recognises
  only prototype items; any unknown item receives a minimal default classification.
- NL trip parsing falls back to `parseConditionsHeuristic` — a deterministic keyword-to-enum
  map. Conservative: unrecognised text yields mild defaults; the user can always use the
  structured conditions form.
- The `/items/new` and `/plan` pages display a visible notice that the offline mode is active.

**`APP_PASSWORD`**

When set, `src/middleware.ts` enforces a session cookie gate on every route except `/login`.
Visiting any page without the cookie redirects to `/login`; submitting the correct password
sets a `httpOnly; SameSite=lax` session cookie.

When absent, the gate is disabled and the app is open — useful for local dev. Do not leave
unset in a production deployment if you want access control.

This is a **v0 one-password gate, not real auth.** A single fixed user backs all rows
(see `ARMARIUM_USER_ID`). Multi-user auth is out of scope for Phase 2.

**`ARMARIUM_USER_ID`**

The UUID recorded as `user_id` on all items and trips. Must be a valid UUID. Controls which
rows are visible: all queries are `WHERE user_id = $userId`. The seed script uses this variable
to target a specific user when populating the database.

## Build and CI — no secrets needed

```bash
pnpm install
pnpm typecheck   # zero errors required
pnpm lint        # zero warnings/errors required
pnpm test        # 51 tests (vitest, offline, no DB/API key)
pnpm build       # hard gate — must pass before any deploy
```

None of these commands need `DATABASE_URL` or `ANTHROPIC_API_KEY`. CI should run without them.
Never add secrets to CI environment unless a step explicitly requires a live DB or API call.

## Supabase setup

1. Create a new Supabase project at [supabase.com](https://supabase.com).
2. Copy the **pooled connection string** (Project Settings > Database > Connection string > URI,
   port 6543) and append `?pgbouncer=true&connection_limit=1` if using PgBouncer pooling.
3. Set `DATABASE_URL` to this string in Vercel environment variables and/or `.env.local`.

---

## Database migration

Migration SQL was generated by `drizzle-kit` (`pnpm db:generate`) and committed to `drizzle/`.
You do not need to regenerate migrations on a fresh deploy — the SQL files are already present.
Run `pnpm db:generate` only when the Drizzle schema (`src/db/schema.ts`) changes.

Apply all pending migrations to the Supabase database:

```bash
DATABASE_URL="postgresql://..." pnpm db:migrate
```

This runs `drizzle-kit migrate` and applies the two migration files in order:
- `drizzle/0000_strong_supernaut.sql` — initial schema (Phase 1)
- `drizzle/0001_clammy_gertrude_yorkes.sql` — adds `items.classification` (jsonb NOT NULL) and
  `items.draft` (boolean NOT NULL DEFAULT false)

The migration command only needs `DATABASE_URL` — no API key is required. Run it once against a
new database; Drizzle tracks applied migrations in a `__drizzle_migrations` table.

## Seed (optional)

The seed script populates the prototype gear corpus for the configured user. It is optional — the
app works with an empty database. Seed only if you want the prototype items present after a fresh
migration.

```bash
# Offline seed (uses pre-validated corpus; no LLM calls):
DATABASE_URL="postgresql://..." pnpm db:seed

# Live seed (classifies each item with the real LLM; higher fidelity):
DATABASE_URL="postgresql://..." ANTHROPIC_API_KEY="sk-ant-..." pnpm db:seed

# Seed for a specific user ID:
DATABASE_URL="postgresql://..." ARMARIUM_USER_ID="your-uuid" pnpm db:seed
```

The script guards against accidental execution: it exits immediately with an error if
`DATABASE_URL` is not set. There is no `dotenv` dependency — pass variables inline (as above)
or via `node --env-file=.env.local` on Node >= 20.6.

The script guards against duplicates: it checks for existing items first and **skips seeding
entirely** (logging a message) if the `items` table is non-empty. To re-seed from scratch, truncate
the `items` table first, then re-run.

## Vercel deploy

1. Connect the repository to a Vercel project (Import > select repo).
2. Framework preset: **Next.js** (detected automatically).
3. Build command: `pnpm build` (or leave as default — Vercel auto-detects `pnpm`).
4. Output directory: `.next` (default).
5. Set environment variables (Project Settings > Environment Variables):
   - `DATABASE_URL` — Production + Preview
   - `ANTHROPIC_API_KEY` — Production + Preview
   - `APP_PASSWORD` — Production only (or Preview if you want the gate there)
   - `ARMARIUM_USER_ID` — Production (if you want a specific UUID; default is fine)
6. Deploy. Vercel builds from `pnpm build`; the build passes with no `DATABASE_URL` or API key
   because all clients are lazy. The running serverless functions connect to the DB on first
   request.
7. After the first successful deploy, run the migration command (step above) against your Supabase
   database if you haven't already. Migrations are not run automatically on deploy.

### Branch / preview deploys

Vercel creates a preview deploy for each branch/PR. If `DATABASE_URL` is scoped to Preview, the
preview will use Postgres. If you prefer, scope `DATABASE_URL` to Production only and let
previews run in ephemeral in-memory mode (no DB, data lost between requests).

## Security notes

- **Secrets never go into git.** `.env.local` is gitignored. Vercel env vars are injected at
  build/runtime and never appear in the repository.
- **`APP_PASSWORD` is a v0 single-password gate**, not real authentication. It controls access to
  the UI only. The database connection string is the true secret protecting stored data.
- **One fixed user.** All items and trips are stored under one `user_id`. The `user_id` is
  present on every row from day one (architecture rule #4) but multi-user isolation is not
  enforced in Phase 2 — the route handlers use `DEFAULT_USER_ID` from `src/server/services.ts`.
- **No LLM output reaches the DB unvalidated.** Classification results are Zod-validated before
  any insert; NL trip conditions are Zod-validated before `deriveRequirements` is called. See
  ADR-0004 and ADR-0006 for the contract.

## Local dev (no Supabase)

```bash
pnpm install
pnpm dev         # starts Next.js dev server on http://localhost:3000
```

Without `DATABASE_URL` the app uses the in-memory repository. Without `ANTHROPIC_API_KEY` the
app uses the offline classifier and heuristic parser. No external services are required to run
locally.

To develop against a real Supabase database locally, add `.env.local`:

```
DATABASE_URL=postgresql://...
ANTHROPIC_API_KEY=sk-ant-...
APP_PASSWORD=yourpassword
```

Then run migrations (`pnpm db:migrate`) and optionally seed (`pnpm db:seed`) before starting the
dev server.
